# IPTV Merge Manager v0.3.3 Release Notes

Build date: 2026-08-14

## Guarded HLS Segment Resilience

v0.3.3 addresses the second failure mode discovered after v0.3.2 fixed FFmpeg's rejection of extensionless commercial-break segment URLs: some provider ad segments can accept the request and then stop producing media indefinitely. In that state FFmpeg remains alive at the same timestamp and its reported average speed continually falls instead of receiving EOF or an HTTP failure.

### What changed

v0.3.2 created a synthetic safe-extension URL and returned an HTTP redirect to the original provider segment. Once FFmpeg followed that redirect, IPTV Merge Manager could no longer enforce any timeout.

v0.3.3 keeps the synthetic alias, but that exceptional alias is now served through a **guarded selective relay**. Only extensionless/unsupported compatibility segments take this path. Recognized media URLs such as ordinary `.ts` and `.m4s` segments continue to go directly from Jellyfin to the provider/CDN.

### Default circuit breaker

- Connect timeout: **4 seconds**
- First-media timeout: **6 seconds** (preflight is bounded by connect + first-media)
- Read-idle timeout: **10 seconds**
- Per-attempt absolute deadline: **20 seconds**
- Failed-segment playlist refresh timeout: **4 seconds**
- Maximum pre-media attempts: **2**
- Relay chunk size: **128 KiB**

The first media chunk is acquired before the response is committed to Jellyfin. This allows a clean bounded retry or 504 when the provider never produces media. Before a pre-media retry, IPTV Merge Manager can refresh the same upstream media playlist and retry a replacement URL only when it maps to the exact same `#EXT-X-MEDIA-SEQUENCE` value. It never jumps ahead to another sequence.

After bytes have been sent, v0.3.3 does **not** retry the segment from byte zero. Doing so would concatenate a restarted segment onto partial MPEG-TS/fMP4 and create deliberate corruption. Instead, if the upstream goes idle or exceeds its deadline, IPTV Merge Manager closes the segment response so FFmpeg can reload the live playlist rather than block forever.

### Downstream cancellation

The relay watches for the downstream request disappearing and also cleans up correctly when Starlette cancels the response task. The corresponding provider response and HTTP client are closed in `finally`, preventing abandoned compatibility requests from remaining resident inside IPTV Merge Manager.

### Diagnostics

New global/per-channel counters include:

- guarded segment relays
- relay retries
- relay timeouts
- downstream cancellations
- completed relays
- relay failures
- media-playlist recovery refreshes
- same-sequence URL recoveries
- relayed bytes

Recent per-channel events record timeout, retry, recovery, stale-segment abort, failure, and downstream cancellation conditions. Existing extensionless-segment, discontinuity, CDN-switch, variant re-resolve, bypass, and failure diagnostics remain.

### Environment controls

```yaml
HLS_SEGMENT_CONNECT_TIMEOUT: "4"
HLS_SEGMENT_FIRST_BYTE_TIMEOUT: "6"
HLS_SEGMENT_READ_IDLE_TIMEOUT: "10"
HLS_SEGMENT_TOTAL_TIMEOUT: "20"
HLS_SEGMENT_PLAYLIST_REFRESH_TIMEOUT: "4"
HLS_SEGMENT_MAX_ATTEMPTS: "2"
```

Advanced optional environment variables remain available in code for token TTL/registry sizing, event history, user agent, and relay chunk sizing.

### Resource impact

This is intentionally **not** a full-stream proxy. Normal recognized HLS media stays direct. Only the synthetic compatibility segments already routed through IPTV Merge Manager by v0.3.2 now carry media bytes through the web process. The relay streams chunks and does not buffer entire segments in RAM or invoke FFmpeg/transcoding.

### Upgrade behavior

The SQLite schema does not change in v0.3.3. Existing v0.3.2 settings, channel selections, HLS modes, source inheritance, channel metadata, EPG data, and output configuration remain compatible.
