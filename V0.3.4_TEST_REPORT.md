## FFmpeg bounded-failure integration check

A local HLS server was used to serve a short playlist containing a valid MPEG-TS segment, a deliberately failed segment that returns HTTP `410 Gone`, an HLS discontinuity, and then another valid MPEG-TS segment. FFmpeg 7.1.5 was run against that playlist. It logged the failed segment, marked it as skipped, opened the following segment, and exited normally with return code `0`.

This validates the key v0.3.4 failure-path assumption: after Protected Playback exhausts its bounded atomic-download attempts, returning `410` allows FFmpeg's HLS demuxer to advance instead of waiting indefinitely on a half-open media response.

## Upgrade-package integration check

The final upgrade ZIP was overlaid onto an extracted copy of the exact v0.3.3 release. Sentinel files were placed in both `data/` and `output/` before the upgrade. After extraction, both sentinels remained intact, the upgraded source reported v0.3.4, JavaScript syntax validation passed, and all **21 tests passed again** from the upgraded tree.

## Runtime limitation of this build environment

The environment used to assemble this release does not have the project Docker runtime available for an actual `docker build`, and APScheduler is not installed in the host Python environment. The application import was therefore smoke-tested with a small APScheduler stub, while the Docker image continues to install the pinned dependencies from `requirements.txt`.

Outbound provider/CDN playback cannot be reproduced in this build environment. The protected-segment tests instead use local HTTP servers that deliberately emulate the exact failure classes v0.3.4 is designed to handle: complete segment delivery, repeated request/cache reuse, and an upstream response that sends initial bytes and then stalls before completing the declared segment body.
